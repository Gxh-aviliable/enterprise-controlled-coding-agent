# 开源 Agent 调研与改进计划

**建议方向：把现有项目做成“修改有依据、结果可验证、过程可控制”的工程工作台。先提高任务完成的可信度和日常使用体验，再决定是否扩展 Agent 数量、集成数量和基础设施。**

本轮只调研、检查代码和编写计划，没有修改应用、数据库、镜像或服务器，没有调用付费模型，没有安装所调研项目。GitHub 连接功能继续保持撤除状态；调研 GitHub 上的开源项目不意味着重新引入 GitHub 连接页面。

## 1. 调研范围和证据口径

- 检查原工作区 feature/multi-agent-plan-a，以及实际部署来源 ../my_mini_claude_code-github-mvp 中相关实现；保留所有已有未提交修改，没有创建/切换分支，没有提交/推送。
- 覆盖 Agent 图与验证门、项目发现、工具契约、Shell/文件变更发布、HITL、SSE/取消、子任务、Trace、前端工作台、镜像和评测报告。
- 外部采用维护方 GitHub 仓库、官方文档及选定源码。不是六个项目的全仓安全审计，也没有运行其 benchmark。
- 阅读时点为 2026-09-14。GitHub 匿名 API 查询默认分支 SHA 遇到 403 rate limit，未取得统一固定提交；以下外部链接主要是动态分支/文档，只证明本次读取的内容。实际移植前应固定提交、检查许可证和相关目录的例外条款。没有用未经核实的星数、排行榜分数做优先级依据。
- OpenHands 当前主仓库描述已转为 Agent Canvas，执行核心在 software-agent-sdk；没有把旧版 Runtime 文档当作当前全部架构。OpenCode V2 权限名称与 V1 不同，以下以明确标为 V2 的文档为依据。

## 2. 代表项目：学什么，以及不照搬什么

| 项目及定位 | 核查的设计 | 对本项目的用处 | 不直接照搬 |
|---|---|---|---|
| [OpenHands](https://github.com/OpenHands/OpenHands) / [Software Agent SDK](https://github.com/OpenHands/software-agent-sdk)：工程 Agent 平台与执行核心 | UI、Agent Server、执行工作区有明确职责；持久化区分状态和增量事件。[持久化说明](https://docs.openhands.dev/sdk/guides/convo-persistence) | 将任务控制、事件展示、容器执行分清；审视断线/重启和 Trace 写入成本 | 不整体迁移 SDK，不为当前单机提前引入 Kubernetes 或多服务集群 |
| [Aider](https://github.com/Aider-AI/aider)：面向代码修改的助手 | 按相关性和 token 预算选取符号信息；可在编辑后运行 lint/test。[Repo map](https://github.com/Aider-AI/aider/blob/main/aider/website/docs/repomap.md)、[测试闭环](https://aider.chat/docs/usage/lint-test.html) | 改善“找对文件→最小修改→相关验证”链路 | 不直接加入整套 Tree-sitter/图排名依赖，也不照搬自动提交策略 |
| [Cline](https://github.com/cline/cline)：IDE/CLI 工程助手 | 通过独立 shadow Git 保存 checkpoint，提供 Compare/Restore。[Checkpoint 文档](https://docs.cline.bot/core-workflows/checkpoints) | 用户应该能看到本任务改了哪些文件，并在无冲突时恢复文件 | 不复制宿主 Git 执行边界；不把恢复文件说成撤销网络/数据库副作用；不增加一个独立 GitHub 页面 |
| [OpenCode](https://github.com/anomalyco/opencode)：交互式 coding agent | V2 明确 allow/ask/deny 和单次/持续批准；文档承认 Shell 目录推断是尽力而为。[V2 权限](https://opencode.ai/v2/docs/permissions) | 审批说明要让用户知道为什么询问、批准的范围是什么 | 不把命令通配符当隔离边界；不照搬子 Agent 权限独立于父权限的规则，继续保持本项目只读子任务和父能力上限 |
| [mini-SWE-agent](https://github.com/SWE-agent/mini-swe-agent)：最小工程 Agent 与评测基线 | 简单循环、Shell 操作、线性轨迹；源码将模型调用、环境执行、步数/费用限制和轨迹保存分开。[核心源码](https://raw.githubusercontent.com/SWE-agent/mini-swe-agent/main/src/minisweagent/agents/default.py) | 保持标准 Shell 的可组合性，减少不必要工具和编排；强化可复现轨迹 | 不删除本项目的多用户认证、HITL、沙箱和取消；其研究基线不等于企业平台 |
| [Deep Agents](https://github.com/langchain-ai/deepagents)：基于 LangGraph 的 Agent harness | 支持隔离子上下文、文件后端、工具输出卸载和摘要；摘要代码记录卸载失败。[摘要源码](https://raw.githubusercontent.com/langchain-ai/deepagents/master/libs/deepagents/deepagents/middleware/summarization.py) | 检查当前压缩后证据能否恢复，评测子任务收益与上下文成本 | 不因为技术栈接近就替换现有 graph；本项目已有 artifact-first、摘要、HITL 和只读委派，优先补证据 |

这些项目解决的问题并不完全相同。框架、个人桌面助手、研究基线和多用户平台不能仅按功能数量横向排名；本项目的价值可以落在受控执行、证据完整性与可追溯性。

### 2.1 源码层面提炼的三个原则

1. **限制要进入执行路径。** mini-SWE-agent 的成本/步骤检查在 query 前，执行通过 environment；本项目继续在 Tool Contract、执行器和权限层实施约束，不能靠一段系统提示维持安全。
2. **上下文要有预算和来源。** Aider 的 [repomap.py](https://raw.githubusercontent.com/Aider-AI/aider/main/aider/repomap.py) 将排名结果裁剪到预算并缓存。适合借鉴目标，不必照搬其依赖组合；本项目先尝试路径/符号的确定性召回。
3. **保存状态不等于恢复副作用。** OpenHands 的事件与状态分离、LangGraph 的 [checkpointer/store 区分](https://docs.langchain.com/oss/python/langgraph/persistence) 都可作设计参考；本项目仍须处理容器已写文件但 checkpoint 未落盘的窗口，不能宣称 exactly-once。

## 3. 当前项目：已有基础与实际差距

### 3.1 已有能力应保留，不要重复建设

| 现有能力 | 已检查位置 | 判断 |
|---|---|---|
| 有状态主循环、重试、验证门和终态检查 | enterprise_agent/core/agent/graph.py、nodes.py、state.py | 具备基础，重点修正证据语义 |
| 项目语言、依赖管理器、命令和 AGENTS.md 发现 | enterprise_agent/core/agent/project_context.py | 已有有界扫描，不应再计划“从零添加项目识别” |
| 统一工具契约、HITL、权限和幂等重试区分 | tools/contracts.py、nodes.py、api/routes/chat.py | 保留；审批体验优化不能绕过执行边界 |
| Docker Shell、过滤快照、冲突检测、取消、reaper | enterprise_agent/sandbox/、tools/workspace_lock.py | 已有可用实现；变更收据利用及异常中断需补齐 |
| 并行只读子任务与父任务预算/归属 | core/execution/children.py、child_store.py、child_workspace.py | 已有真实演示；效果收益尚未正式对照 |
| artifact、上下文压缩、三层记忆治理 | tool_artifacts.py、context.py、docs/memory-governance.md | 不新增另一套记忆框架，先测质量与成本 |
| 用户文件编辑与 SHA-256 冲突拒绝 | api/routes/workspace.py、frontend/src/components/FileViewer.vue | 已有单文件编辑能力；缺少任务级改动总览与安全恢复 |
| benchmark 与隐藏检查 | benchmarks/run.py、benchmarks/v2/cases.json | 已有 30 例，不应重新造评测平台 |

### 3.2 已确认的问题，及需要补验的边界

**A. 验证门的成功依据过弱——代码检查和函数探针已确认。**

- nodes.py:864 的 _is_validation_command 使用关键词子串；函数探针显示 echo pytest 被判为验证命令。这里没有执行该 Shell 命令，验证的是分类函数实际行为。
- nodes.py:869 只要 validation_results 中曾有 ok=true 就认可成功；探针显示“当前 app.py 已改动 + 以前一次 pytest 成功”仍不要求新验证。没有输入版本、执行时间与改动序号约束。
- nodes.py:2503 附近的 changed_files 只从 write_file/edit_file/delete_paths 更新。沙箱 executor.py:221 已提供 published_paths，但主节点尚未把 Shell 发布路径纳入这一集合。需要把已有可信发布结果接入，不必新造 Git 检测器。
- 这些是验证完整性缺口，并非本轮发现了沙箱逃逸；也不代表所有真实任务都会被误判成功。

**B. 当前发布版本缺少同口径模型质量基线——已有报告确认。**

正式 Agent v2 报告是 2026-08-27、源码 1d637c5 的 23/30；平均 53,128.93 token、平均 16.840 秒。它不能代表 9 月新增沙箱、Multi、移除 GitHub 后的版本。Platform 30/30 是确定性工具/夹具证据，不能替代模型成功率。

旧报告的失败提供排查线索：小修改没有执行要求的验证，Decimal 精度和 TTL 边界遗漏，重构要求未满足；提示注入用例曾在解释拒绝攻击时复述禁止输出的 canary。最后一项是旧运行中可见的输出泄露，不证明当前版本仍复现；应优先重测，不能通过降低判分标准消除失败。检查器也有结构/格式约束，需保留其用途并单独记录是否存在过度限定，修改检查器必须版本化。

**C. 用户能看到工具过程，但不容易直接验收修改——界面检查。**

FileViewer 有安全读取/编辑和冲突保护；本次未发现任务级新增/修改/删除清单、统一 Diff 和按本任务恢复文件入口。改善现有聊天结果区域即可，不需要新增顶层导航。

**D. 已有断线恢复控制，但不能等同于持久任务执行——代码与证据边界。**

chat.py 有 stream/status、任务归属、runner fence、取消和历史恢复；图执行仍出现在 StreamingResponse 生成器内，_sse_event 仅输出 data 字段，未提供统一 SSE id/cursor 重放协议。不能据此断言所有刷新都会丢任务，但必须补断网、刷新、kill API 的实际测试，再决定解耦程度。

**E. 语言识别能力大于默认执行镜像能力——Dockerfile 检查。**

project_context 可以识别多种语言，而默认 sandbox 镜像主要为 Python + pytest。识别出 npm run build 不等于容器可以运行它。缺失依赖是环境问题，不应让模型反复尝试联网安装或被算作代码质量失败。

**F. 运维与多副本能力存在清晰上限——不必立刻重构。**

TraceStore 使用进程内 RLock 和整份 JSON 原子替换；适合当前单进程，不支持直接推导多进程并发安全。沙箱 publish 先校验再逐文件发布，不是整个目录原子事务。三个关键文件分别约 3388、3528、2398 行，维护成本可见，但行数本身不是重写理由。

来源摘要与函数探针结果保存于 [本地调研证据](release-evidence/agent-plan-audit-20260914.json)。

## 4. 优先级总表

| 顺序 | 优先级 | 工作包 | 直接收益 | 粗估 | 依赖 |
|---|---|---|---|---:|---|
| 1 | P0 | A：固定发布来源与版本证据 | 防止继续改错工作区、演示与证据不一致 | 0.5–1 人日 | 无 |
| 2 | P0 | B：统一变更收据与验证版本绑定 | 防止没有真实验证却报告成功 | 2–4 人日 | A |
| 3 | P0 | C：浏览器演示回归与当前质量基线 | 找到真实失败，确保展示链路可复现 | 2–4 人日 | A；正式结果在 B 后 |
| 4 | P1 | D：任务改动清单、Diff、安全恢复 | 用户直接判断 Agent 是否改对 | 3–5 人日 | B |
| 5 | P1 | E：有预算的代码定位与上下文 | 减少盲目扫描和重复读取 | 2–4 人日 | C |
| 6 | P1 | F：最小执行环境预检与受控镜像 | 让测试命令真正可执行 | 1–3 人日 | C |

P0 合计约 4.5–9 人日；不要把整张表承诺为一个冲刺。模型评测时间、费用和失败分析另受模型速度、预算影响。

## 5. 工作包实施与验收

### A / P0：确定唯一开发、发布和评测来源

问题：原工作区和实际部署工作区并存，历史证据、镜像版本及部分能力文档时间不同。

实施：生成一份不含凭据的 release manifest，记录源码摘要、锁文件摘要、镜像 digest、迁移 revision 和测试报告。先在既有健康/版本信息中体现版本，不做新页面。核对两工作区差异后再安排整合；不得复制整个目录覆盖已有修改。较大代码改进按 AGENTS.md 从 develop 安排 feature/*，需要带入未提交改动时先保存差异清单。

验收：从清单可以确认本地源码、构建镜像、运行服务和评测产物的对应关系；没有凭据和用户文件；无差异文件被意外覆盖。维护 docs/capability-matrix.md，历史成绩保留日期，不升级成当前成绩。

风险：已有 benchmark --official 要求干净提交；当前未提交树不满足。开发期间只能发布诊断结果或增加明确命名的 snapshot-qualified 报告，不能冒充原 --official。是否提交按用户后续授权处理。

### B / P0：让“已完成”绑定真实修改和验证

实施：复用 sandbox 的 published_paths、workspace_lock、现有 inventory/hash 和 ToolExecutionRecord，形成统一变更收据；文件工具、Shell、后台 Shell 都覆盖。记录 before/after 摘要、操作序号、trace_id、tool_call_id 和失败时已经发布的路径。部分副作用不能因工具返回失败就消失。

验证记录关联工作区输入版本、实际执行器、命令/argv、cwd、退出码、超时/取消状态、输出摘要。写入新版本后旧验证失效；验证过程中用户编辑或验证命令自身改源码时，保守失效并解释。排除 pytest 缓存等非源码变化，规则应确定且可测试。

删除“关键词出现即验证”的判断。第一版只认一小组明确的测试/构建/静态检查入口，简单 Shell 形式可转换为明确 argv；复合命令、别名和自定义脚本仍允许按原 Shell 权限执行，但无法确认验证语义时显示“命令完成，验证未确认”。shlex 不能解析任意 Shell 语义，不为此写一个通用 Shell 解释器；也不新增一批模型专用测试工具。项目声明的 test 脚本仍是不可信代码，运行仍在沙箱/HITL 边界内。

区分测试、构建、lint 和语法检查；语法检查通过不等于行为正确。“验证通过”仅证明特定命令在特定版本运行成功，不是数学证明修复正确。任意自定义报告不能因带有 JUnit 文件就被信任。

验收用例至少包括：echo pytest；pytest --version；pytest 失败后 || true；测试成功后改文件；Shell 单独改源码；后台任务改源码；验证期间并发编辑；验证命令改源码；超时/取消；测试无法运行。前三类不得被报为行为测试通过；所有无法确认的代码修改不能直接得到 succeeded。只读问答仍可正常完成。

涉及：nodes.py、state.py、tools/contracts.py、sandbox/executor.py、文件/后台工具及 lifecycle 测试。尽量在共享边界修复，避免各工具各维护一套规则。

### C / P0：当前基线、失败分类和真实浏览器回归

实施分两层：

1. 用本地独立账号/夹具做 5 条真实浏览器链路：登录→读取；修改→审批→验证→结果；拒绝审批；执行中 Stop→新任务；刷新/短断网→历史和权威状态一致。保留截图、Trace、文件最终摘要，失败能定位；不要用组件测试替代这些链路。
2. 复用 v2 30 例，先跑离线 platform，再对当前源码运行模型诊断；对 7 个旧失败逐类核对。在预算确定后做重复运行，所有失败保留，不挑最好一次。新安全压力集与旧 v2 分开版本化，覆盖“解释拒绝时复述秘密”、README/AGENTS/日志中的注入、跨用户产物访问。

验收：演示夹具明确范围、起始文件和期望断言；模型不完成时显示实际失败，不切换假结果。指标同时报告任务成功率、infra/system error、工具成功率、p50/p95 时间、输入/输出 token、审批次数和安全泄露。infra 失败不能悄悄从用户可见可用性统计中消失。

演示用例建议：Python 小缺陷修复、拒绝不允许操作、双只读子任务调查后由主 Agent 修改。真实模型演示与确定性平台演示明确标注。还没有 Node 镜像前不承诺现场演示前端构建。

### D / P1：在聊天结果中显示本任务改动，随后支持恢复

第一步只做结果卡：新增/修改/删除文件、可展开 Diff、验证命令和版本、未完成项；复用 FileViewer 与现有聊天/Trace 区域，不增加顶层设置页。Diff 来自可信 before/after 收据，不让模型自述充当事实。

第二步保存有限文本文件的修改前内容，提供“恢复本任务文件”。恢复前逐文件比对当前摘要是否等于本任务 after 摘要，有后续修改就整体拒绝并指出冲突；记录恢复事件。非 Git 工作区也支持。不恢复聊天状态，不回滚数据库/网络，不碰用户 Git 元数据。

二进制、超大文件、敏感路径、符号链接明确显示不支持恢复；开始变更前告知覆盖范围。内容快照放在按用户隔离的控制存储，执行容器不可写。设置按任务的大小/数量/保留期上限。多文件恢复需要预检与恢复日志，崩溃后可确定哪些已应用，不能声称整个文件树原子回滚。

验收：文件工具与 Shell 改动都显示；两用户不互见；用户后续编辑不被覆盖；取消后的已发布修改仍可查看；清理历史快照不损坏当前文件。

### E / P1：提高代码定位效率，不再增加一套项目发现

先记录当前 project_context 的大小、耗时、缓存命中和后续重复读取次数。利用已有工程命令识别、目录信息和 rg，按用户指定路径/标识符优先检索；Python 符号可先用 ast，其他语言先用文本索引。只有基准显示文本方法不足时再引入 Tree-sitter。

缓存必须包含用户/工作区身份和内容版本，不复用其他用户目录。给摘要独立 token 上限，返回出处和可继续读取的路径；敏感文件和 Agent 控制路径沿用现有排除规则。已有摘要、artifact-first 和压缩流程保留，补过期指针/读取失败的准确提示。

验收：在固定定位任务集上，比较成功率与首次找对文件前的调用数、总 token、p95 耗时；可先设 token 中位数下降 20% 为试验目标，但不提前承诺达成。未改善则撤回新索引，不保留无效复杂度。

### F / P1：执行环境预检与最小受控镜像

主任务开始测试前检查已安装运行时及必要测试器，将识别出的工程命令与镜像能力匹配。先只提供实际用到的 Python、Node 两类由管理员构建的镜像，固定依赖和 digest；是否需要项目依赖预装由真实示例确定。

普通执行继续禁网、非 root、只读根、资源限制。模型不得指定任意镜像、宿主挂载、凭据或出口策略。缺少 Node/依赖时明确 environment_unavailable，不自动回退宿主执行，不反复联网安装。不做通用 Dockerfile 上传/在线构建平台。

验收：Python 和 Node 各一条真实测试链路；不存在的运行时、Docker 故障和依赖缺失均有明确分类；模型任务失败统计区分环境准备不足。

### G / P1：先规定断线与重启行为，再决定持久执行拆分

先写故障矩阵：浏览器断开、用户 Stop、审批等待、API 被杀、Redis 不可用、容器执行完但终态未写入。原有 Stop 终态、新 Trace 重新规划和 runner fence 继续作为基础。

短期目标是结果和状态可恢复：关键事件具有 trace_id、单调 seq、owner 和 fence，可用 cursor 补取；重启后残留 running 收敛为 interrupted/待核对，展示可能已发生的文件改动。不得自动重放非幂等写操作。对终态写入失败和半发布窗口做故障注入。

只有明确要求“关闭页面后继续长任务”时，才把 graph runner 从 SSE 请求生命周期分离，使用现有 Redis/任务控制能力；先单 worker，不新增 Kafka/Celery。API 只订阅事件，Stop 仍通过权威控制链路。数据库/队列记录和 filesystem 副作用没有天然事务，需以收据核对。

验收：断线重连不产生重复写入或重复审批，乱序事件不覆盖终态；其他用户不能补取事件；kill API 后不永久显示 running；无法确认的操作明确显示未知/待核对，而不是自动报失败后重做。

### H / P1：在现有 HITL 卡片解释批准对象

展示实际工具、目标路径/命令、修改范围、风险原因和批准有效期；复用现有策略。第一阶段只改善内容、重复提交幂等性和过期提示，不改变权限默认值。

若数据显示同任务重复审批明显影响使用，再设计绑定参数与工作区版本的有限授权；参数、路径、任务、用户或权限变化都要失效。不能以“测试命令”为名自动允许任意项目脚本，也不能降低权限来追求更低审批率。

验收：旧审批无法授权新参数；拒绝/过期后没有副作用；运行状态与审批卡一致；原只读子 Agent 不获得写入或 Shell。

### I / P1：用对照结果决定 Multi 的使用场景

复用已有 6 个 delegation_suitable 用例。相同代码、模型、环境、任务总预算和审批策略下，分别跑 Single/Multi；至少 3 次配对作为探索性样本，交换执行顺序并保留每次结果。不把 18 次样本解读成普遍统计结论。

报告成功率、wall time、累计 token、重复读取、父任务剩余预算和子失败处理。若没有成功率或延时收益、成本明显上升，继续 Single 默认并缩小 Multi 推荐范围。先优化任务说明和上下文供给，不增加写子 Agent、自治团队或多层委派。

验收：能从证据看到子任务并行时间、各自输入范围、输出何时被主 Agent 使用，以及主修改发生在读取子结果之后；不根据卡片数量声称协作有效。

### J / P2：记忆效果评测，而非换框架

将现有 6 例扩展到约 20 个有版本的数据用例，分准入、相关召回、无关拒绝、偏好更新、级联删除、跨用户隔离和模型实际采用。新增“当前指令覆盖旧偏好”和错误记忆反例。

沿用 Redis/MySQL/Chroma 职责和 provenance；不用 Mem0/Letta 替换当前栈。报告 admission precision/recall、无关注入率、跨用户泄露、模型行为符合率和额外 token；不能以 retrieval=100% 推导 memory 有效。

### K / P2：按真实负载处理 Trace 和存储

先测每任务事件数、JSON 文件大小、写入耗时、磁盘增长和查询延时，补保留期限、容量告警与可恢复备份演练。当前维持单写进程；若要多 worker 或集中审计，优先使用现有 MySQL 保存有唯一键的增量事件和任务摘要，而不是再引入一种数据库。

受信审计记录与用户可写 workspace 分开；模型/执行容器不能篡改，API 按身份授权查看。事件需脱敏，密钥不能进入持久日志。重放/查询索引、保留期和清理竞态一并验收；受限证据 artifact 仍不等于永久完整审计。

### L / P2：只沿实际变更做拆分和清理

在 B/G/H 修改时，分别抽出验证收据、流事件协议、审批序列化等已有职责，保持单一实现和现有契约测试；不要把三千行文件简单搬成多层 service/factory/interface。

已撤除 GitHub 模块的永久删除、旧 team 代码清理应单列兼容性检查：确认没有旧 checkpoint、迁移或恢复资料依赖。只清理代码不清理用户仓库、历史配置或私有备份；不要因一次删除任务自动销毁数据。

## 6. 面试展示与长期建设分开安排

如果展示就在近期：冻结当前服务，先完成 A 和 C 的已有流程演练；只修确定会阻断展示的小问题。B 在本地验证后发布，来不及则如实说明验证门边界，不在展示前夜做大范围状态机重构。

建议演示顺序：读取已有示例 → 定位故障 → 审批 → 修改 → 真实测试 → 查看文件与 Trace → Stop/新任务；Multi 用单独、已预演的只读探索案例。真实失败允许出现，但失败后应清楚指出状态和证据。用户数据不作测试夹具。

后续迭代顺序：A/B/C → D；E/F 由 C 的失败归因确定先后；G/H 改善长任务体验；I 决定 Multi 投入；J/K/L 按证据触发。可以先交付 Diff 展示，再交付恢复，不将全部功能捆绑发布。

## 7. 暂不投入的方向

- 重新上线 GitHub 连接页、PR/Issue 平台或通用上传平台。
- 写入型多 Agent、复杂自治团队、任务市场、插件市场。
- 向量数据库迁移、GraphRAG、全仓知识图谱，除非代码定位/记忆评测先证明需要。
- 企业完整 SSO/RBAC、多租户计费、Kubernetes、微服务拆分，除非出现明确客户/规模需求。
- 自动发布、自动回滚外部副作用、默认全面自动审批。
- 仅为文件行数做整仓重构，或仅为榜单表现换模型/框架。

近期最值得交付的产品变化是：**每次任务结束，用户能直接看到实际改动、验证依据、未完成事项，并且不会因误判或恢复操作丢失自己的修改。**
